# Formetrix Project Control Dashboard — Architecture

> This document designs, but does not build, a project-control system: a
> browser dashboard showing milestones, tickets, decisions, releases,
> progress, and status. It defines the structured data model that would
> power it and every other consumer (Excel, PDF, GitHub Issues, Claude Code
> automation), the dashboard's information architecture, and the update/
> validation/audit workflow around all of it.
>
> Nothing in this document is implemented. No `management/data/` files
> exist yet — every schema below is design, with inline examples. No
> dashboard UI, hook, or export exists. See §16 for what to build first.

**Status:** Proposed architecture, pending founder decisions (§15).

---

## 1. Purpose

Formetrix currently tracks project governance entirely in Markdown
(`management/`, `docs/`, `FORMETRIX.md`) — human- and AI-readable, git-
diffable, and rich with the reasoning that makes it trustworthy. That has
worked well through 24 tickets, 16 architecture decisions, and 9 founder
decisions. But it has three real limits this document addresses:

1. **Progress is hand-painted.** Every milestone completion percentage in
   `management/MILESTONES.md` — including the ones this session set — is a
   qualitative judgment call written in prose, not a number derived from
   ticket data. That's exactly what this ticket's Milestone Model
   instruction ("progress must be calculated from ticket data") is
   correcting, and §5 shows the gap is real: the formula this document
   proposes currently computes Milestone 0 at **~60%**, not the 80% hand-
   set in `MILESTONES.md` today.
2. **There is no single machine-readable view of project state.** A
   dashboard, an Excel export, a PDF snapshot, and GitHub Issues sync all
   need the same underlying facts. Today, producing any of them means
   re-parsing prose.
3. **Nothing validates the management system against itself.** Every
   inconsistency caught in FM-0021–FM-0023 (mismatched milestone names, a
   ticket referenced before it existed, an unjustified percentage) was
   caught by a human or an AI agent reading carefully — not by a rule that
   runs automatically. §8 and §9 exist to close that gap.

## 2. Scope

In scope: the data model, dashboard information architecture, update
workflow, validation rules, and automation design needed to power a
project-control dashboard. Explicitly out of scope for this ticket, per
its own instructions: the dashboard UI itself, populated production JSON
files, active Claude Code hooks, and any Excel workbook or PDF template.

## 3. Guiding Principles

- **One authoritative writer per fact, always.** Every field in this
  design has exactly one system that may set it and everything else reads
  it — never two systems that can both write the same fact. This is the
  single principle every source-of-truth and validation decision below
  traces back to; see §4.7's relationship map for how it's enforced field
  by field.
- **Computed, not asserted, wherever a computation is possible.** A
  percentage a person types is a percentage that can be wrong, stale, or
  quietly generous. Where this document can define a formula instead
  (progress, rollups, counts), it does — even where the computed number is
  less flattering than the number currently in `MILESTONES.md`.
- **No generated artifact becomes a second source of truth.** Excel, PDF,
  and (if built) generated Markdown are read-only views of the underlying
  data. Editing a generated artifact and expecting it to persist is a bug
  in this design if it's ever possible.
- **Validate before you trust — including this document's own
  recommendations.** The ticket asks to "validate" its suggested
  source-of-truth direction, not adopt it uncritically. §4 does that: it
  keeps the ticket's recommended shape but is explicit about what has to
  be true for it to hold, and flags where the honest answer is "this needs
  the founder's call," not an engineering default.

## 4. Source-of-Truth Architecture

### 4.1 The question

The ticket's preferred direction: structured JSON for machine-readable
state, Markdown for narrative documentation, the dashboard for
presentation, Excel/PDF as generated exports. Two readings of "JSON for
state, Markdown for narrative" are possible, and they lead to different
architectures:

- **(A) JSON is authoritative; Markdown is generated from it.** Every
  ticket, decision, and milestone — including its prose — lives in JSON
  first. `TICKETS.md` et al. become build output, regenerated by a script,
  the same way `dist/` is generated from `src/`.
- **(B) Markdown stays authoritative (as it is today); JSON is a derived,
  read-only index of Markdown's structured fields**, built by parsing it.

### 4.2 Recommendation: (A), with Markdown demoted to generated output — but only once the tooling exists

**(A) is the correct end state**, for one decisive reason: a future
Claude Code hook that updates ticket status after a commit (§10) needs a
reliable place to _write_ to. Writing a JSON field is a solved problem.
Reliably rewriting a specific ticket's `Status:` line inside a large
Markdown file, from a hook, without corrupting neighboring content, is a
much less reliable one — every one of the "unfenced template" and
"milestone name mismatch" bugs caught in FM-0021–FM-0023 originated from
exactly this kind of manual/semi-structured Markdown editing.

**But this is a target architecture, not something to flip today.**
Migrating 24 tickets, 16 decisions, and 9 founder decisions into JSON
accurately is real work (§16), and until the generator/validator tooling
exists, **Markdown remains the operative source of truth** — this
document does not change how anyone edits `management/` today.

### 4.3 The risk this recommendation creates, and how it's closed

The instruction is explicit: _"No generated export should become a
conflicting source of truth."_ Recommendation (A) makes Markdown a
generated export. Two things have to hold, or this design fails on its
own terms:

1. **Single-writer discipline.** Once the pipeline exists, `TICKETS.md`,
   `MILESTONES.md`, and `DECISIONS.md` are written _only_ by the
   generator script, never edited by hand. A pre-commit or CI check (built
   alongside FM-0004) diffs each generated file against what's actually
   committed and fails if they differ — the same category of check that
   already exists for `prettier --check` today.
2. **Nothing is lost in the move.** The richest content in this project's
   Markdown today — dependency-explanation notes (FM-0004's "can be
   scaffolded in parallel..."), the ID-collision note on FM-0021, ADR
   reasoning — has to have a real home in JSON, not be quietly dropped for
   the sake of a clean schema. §4's schemas below keep every one of these
   as first-class string/array fields rather than flattening them away.

If either of those isn't true in practice once this is built, the
recommendation should be reconsidered — that's not a hypothetical
caveat, it's the actual acceptance test for whether (A) was the right
call.

## 4.4 Structured Data Model — `management/data/`

Six files, one JSON object or array each. None exist yet; every example
below is illustrative, drawn from this project's real current state where
possible so the schema can be checked against something concrete rather
than invented data.

### `project-status.json`

**Purpose:** the single computed snapshot that powers the Executive
Overview (§6.1). Not hand-authored — regenerated in full every time the
validation script runs (§10).

| Field                       | Required | Type                                                        | Notes                                                                                                |
| --------------------------- | -------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `generatedAt`               | yes      | ISO datetime                                                | When this snapshot was computed                                                                      |
| `currentMilestoneId`        | yes      | string (milestone id)                                       | The milestone with the earliest `status != complete`                                                 |
| `overallProgressPercent`    | yes      | integer 0–100                                               | See §5.3                                                                                             |
| `milestonesSummary`         | yes      | array of `{id, name, status, progressPercent}`              | Denormalized for a fast dashboard-home read                                                          |
| `ticketCounts`              | yes      | `{backlog, planned, inProgress, blocked, completed, total}` | Must sum correctly                                                                                   |
| `blockedTicketIds`          | yes      | array of string                                             | Empty array, not omitted, when none                                                                  |
| `repositoryState`           | yes      | `{localCommit, remoteCommit, ahead, pushed}`                | Directly motivated by this project's real, recurring "committed locally, not pushed" state (FM-0003) |
| `dataIntegrityWarningCount` | yes      | integer ≥ 0                                                 | See §9                                                                                               |
| `recentActivityIds`         | yes      | array of string, most-recent-first, capped                  | Pointers into `activity.json`                                                                        |

**Ownership:** 100% computed. Never hand-edited; has no meaningful "author."

**Validation rules:** `ticketCounts` fields sum to `total`; every id in
`milestonesSummary`/`blockedTicketIds`/`recentActivityIds` must resolve in
its source file; `generatedAt` may not be in the future.

**Example** (illustrative — computed from this repository's actual state
as of FM-0024, not a real generated file):

### `milestones.json`

**Purpose:** structured form of `management/MILESTONES.md`.

| Field             | Required     | Type                                                            | Notes                                                                                                                                          |
| ----------------- | ------------ | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`              | yes          | string, `"M0"`–`"M5"`                                           | Matches milestone number; never reused (existing rule, carried forward)                                                                        |
| `name`            | yes          | string                                                          | Must match the corresponding Markdown heading verbatim                                                                                         |
| `objective`       | yes          | string                                                          | 1–2 sentences                                                                                                                                  |
| `status`          | yes          | enum: `not_started` \| `in_progress` \| `blocked` \| `complete` | 1:1 with Markdown's four existing values                                                                                                       |
| `startDate`       | no, nullable | date                                                            | **Not currently tracked anywhere in this project** — see §15                                                                                   |
| `targetDate`      | no, nullable | date                                                            | Same as above                                                                                                                                  |
| `completedDate`   | no, nullable | date                                                            | Set when `status` becomes `complete`                                                                                                           |
| `ticketIds`       | yes          | array of string                                                 | **Derived, not authored** — see §4.7; computed by scanning `tickets.json` for matching `milestoneId`                                           |
| `progressPercent` | yes          | integer 0–100                                                   | **Computed, not hand-set** — see §5.2. This is the field that directly answers the ticket's "progress calculated from ticket data" instruction |
| `deliverables`    | yes          | array of string                                                 | Narrative; may reference a ticket by ID inline or state "not yet ticketed," per `MILESTONES.md`'s existing rule                                |
| `blockers`        | yes          | array of `{description, ticketId?, sinceDate}`                  | Empty array today (no milestone is blocked)                                                                                                    |
| `lastUpdatedAt`   | yes          | ISO datetime                                                    |                                                                                                                                                |

**Ownership:** `name`/`objective`/`deliverables`/`blockers` are human- or
AI-authored narrative. `status`/`ticketIds`/`progressPercent` are

this direction, not the reverse.

`tickets.json` with matching `milestoneId`; `completedDate` requires

    "FM-0006",

    "FM-0022",

### `tickets.json`

**Purpose:** structured form of `management/TICKETS.md` — the largest and
most-written-to file.

**Field-by-field necessity evaluation**, as the ticket requested, against
the exact 19 fields it specified:

| Field                | Required     | Type                                                               | Necessary? Why                                                                                                                                                                                                                                           |
| -------------------- | ------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                 | yes          | string, `FM-XXXX`                                                  | Yes — primary key, existing convention unchanged                                                                                                                                                                                                         |
| `title`              | yes          | string                                                             | Yes                                                                                                                                                                                                                                                      |
| `description`        | yes          | string                                                             | Yes                                                                                                                                                                                                                                                      |
| `milestoneId`        | yes          | string                                                             | Yes — **authoritative** direction (§4.7)                                                                                                                                                                                                                 |
| `status`             | yes          | enum: `backlog`\|`planned`\|`in_progress`\|`blocked`\|`completed`  | Yes — 1:1 with the five existing Markdown values                                                                                                                                                                                                         |
| `priority`           | yes          | enum: `high`\|`medium`\|`low`                                      | Yes                                                                                                                                                                                                                                                      |
| `type`               | yes          | enum: `feature`\|`infrastructure`\|`documentation`\|`bug`\|`chore` | Yes, though **new** — not tracked in Markdown today. Earns its place: without it, the Kanban (§6.3) can't separate FM-0013 (Property Search) from FM-0022 (a domain-model document)                                                                      |
| `owner`              | no, nullable | string                                                             | Yes, though thin today (everything is founder + AI agent). Backfilling later, after real multi-user teams exist per FD-0002, is harder than including it now                                                                                             |
| `dependencies`       | yes          | array of `{ticketId, note?}`                                       | Yes — **not** a bare string array. FM-0004's existing dependency note ("can be scaffolded in parallel...") is real, load-bearing content; flattening it to just an ID would lose it                                                                      |
| `acceptanceCriteria` | yes          | array of `{text, met: boolean}`                                    | Yes — and this is what makes `progressPercent` computable rather than asserted (§5.1). This formalizes a pattern already in informal use: FM-0002/FM-0003's Markdown entries already annotate individual criteria "— Met" / "— Not yet met"              |
| `createdAt`          | yes          | ISO datetime                                                       | Yes, though not currently tracked in Markdown — backfill approximately for existing tickets during migration (§16), exact going forward                                                                                                                  |
| `startedAt`          | no, nullable | ISO datetime                                                       | Yes — set when `status` first becomes `in_progress`                                                                                                                                                                                                      |
| `completedAt`        | no, nullable | ISO datetime                                                       | Yes — set when `status` becomes `completed`                                                                                                                                                                                                              |
| `blockedReason`      | no, nullable | string                                                             | Yes, only populated when `status: blocked`. Always null today (nothing is blocked) but cheap to include and needed the first time something is                                                                                                           |
| `commitSha`          | no, nullable | string                                                             | Yes — direct traceability from ticket to the commit that fulfilled it (FORMETRIX.md §7). Real example already exists: FM-0001 → `7e0db87`                                                                                                                |
| `pullRequest`        | no, nullable | string (URL or number)                                             | Yes for forward compatibility with FORMETRIX.md §22's PR-based workflow, even though nothing in this repo has used a PR yet — always null today                                                                                                          |
| `release`            | no, nullable | string (version)                                                   | Yes — links to `releases.json`; null until the first release ships                                                                                                                                                                                       |
| `progressPercent`    | yes          | integer 0–100                                                      | Yes, but **redefined**: not manually set. Computed from `acceptanceCriteria`'s met-ratio (§5.1) — this keeps a ticket-level percent from becoming exactly the kind of "manually painted" number the Milestone Model instruction explicitly warns against |
| `lastUpdatedAt`      | yes          | ISO datetime                                                       | Yes                                                                                                                                                                                                                                                      |

All 19 requested fields are kept — none were dropped. The evaluation
found each one earns its place once given a precise purpose; the main
correction is that four of them (`ticketIds` on milestones, `progressPercent`
on both tickets and milestones, `dependencies`) needed a more specific
shape than "just a field" to avoid becoming stale or lossy.

**Ownership:** `title`/`description`/`acceptanceCriteria[].text`/
`dependencies[].note`/`blockedReason` are authored narrative (human or AI).
`status`/`priority`/`type`/`milestoneId`/`owner`/`dependencies[].ticketId`
are structured, set by whoever performs the action. `createdAt`/
`startedAt`/`completedAt`/`lastUpdatedAt` are event-stamped at the moment
of the relevant transition. `progressPercent` is fully computed.

**Validation rules:** `id` unique, never reused (existing rule); every
`dependencies[].ticketId` and `milestoneId` must resolve; a ticket may not
be `completed` with any `acceptanceCriteria[].met === false`; `blockedReason`
required when `status: blocked`, forbidden otherwise; `startedAt` ≤
`completedAt` when both are set.

### `decisions.json`

**Purpose:** structured form of **both** `management/DECISIONS.md` (ADRs)
and `management/FOUNDER_DECISIONS.md` (FDs) — one file, not two, per the
ticket's naming, but with the conceptual distinction those two documents
deliberately established (FM-0023) preserved via a discriminated `kind`
field, not erased by merging them.

| Field                                    | Required                  | Type                                                     | Notes                                                                                            |
| ---------------------------------------- | ------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `id`                                     | yes                       | string, `ADR-XXXX` or `FD-XXXX`                          | Prefix determines `kind`                                                                         |
| `kind`                                   | yes                       | enum: `architecture` \| `founder`                        | Discriminator                                                                                    |
| `date`                                   | yes                       | date                                                     |                                                                                                  |
| `status`                                 | yes                       | enum: `proposed`\|`approved`\|`superseded`\|`deprecated` | **Harmonized** — see the note below                                                              |
| `decision`                               | yes                       | string                                                   |                                                                                                  |
| `rationale`                              | yes                       | string                                                   | Renamed from Markdown's "Reason" (ADR) / "Rationale" (FD) to one field name                      |
| `alternativesConsidered`                 | `kind: architecture` only | array of string                                          | FD entries don't currently carry this field; not fabricated for them                             |
| `impact`                                 | `kind: architecture` only | string                                                   |                                                                                                  |
| `productImpact` / `deferredImplications` | `kind: founder` only      | string / string                                          | FD's two distinct fields, kept distinct rather than merged into `impact`                         |
| `supersedes` / `supersededBy`            | no, nullable              | string (id)                                              | Formalizes a convention both Markdown docs already describe in prose but don't structurally link |
| `relatedTicketIds`                       | no                        | array of string                                          | Enables the Decision Log (§6.5) to show "decisions relevant to this ticket"                      |
| `lastUpdatedAt`                          | yes                       | ISO datetime                                             |                                                                                                  |

**Note on `status` harmonization:** `management/DECISIONS.md` currently
uses `Accepted` where `management/FOUNDER_DECISIONS.md` uses `Approved`
for the equivalent state. This JSON schema uses one value (`approved`)
for both `kind`s — a real, minor inconsistency this design surfaces (see
§14, Risks) rather than silently perpetuates. The Markdown wording is
**not** changed by this ticket; only the JSON schema is harmonized.

**Ownership:** `kind: architecture` entries may be authored by a human or
an AI engineering agent, matching `DECISIONS.md`'s existing rule.
`kind: founder` entries may only reach `status: approved` via explicit
Founder action — an AI agent may create one at `status: proposed`, never
`approved`, matching `FOUNDER_DECISIONS.md`'s existing rule exactly.

**Validation rules:** `id` prefix must match `kind`; `alternativesConsidered`/
`impact` forbidden (not just optional) when `kind: founder`;
`productImpact`/`deferredImplications` forbidden when `kind: architecture`;
`supersedes`/`supersededBy` must point to an id of the same `kind`; a
`kind: founder` entry's `status` may never be set to `approved` by an
automated process (§13).

### `activity.json`

**Purpose:** append-only event log powering the Activity Feed (§6.6) and
forming the basis of the audit trail (§9). Structurally different from
the other five files — a log, not a collection of mutable entities.

| Field                                                          | Required     | Type                                                                                                                                                                                                                    | Notes                                                                                                                    |
| -------------------------------------------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `id`                                                           | yes          | string, e.g. `ACT-000024` or a ULID                                                                                                                                                                                     | Chronologically sortable by construction                                                                                 |
| `timestamp`                                                    | yes          | ISO datetime                                                                                                                                                                                                            |                                                                                                                          |
| `type`                                                         | yes          | enum (extensible): `ticket_created`\|`ticket_status_changed`\|`ticket_completed`\|`milestone_updated`\|`decision_recorded`\|`founder_decision_approved`\|`commit_created`\|`release_published`\|`management_doc_edited` |                                                                                                                          |
| `actor`                                                        | yes          | string                                                                                                                                                                                                                  | A person's name, or `"AI Engineering Agent"` — matching the participant convention `management/MEETINGS.md` already uses |
| `summary`                                                      | yes          | string                                                                                                                                                                                                                  | One line, human-readable, e.g. `"FM-0021 status changed: planned → completed"`                                           |
| `relatedTicketId` / `relatedDecisionId` / `relatedMilestoneId` | no, nullable | string                                                                                                                                                                                                                  | Whichever applies                                                                                                        |
| `previousValue` / `newValue`                                   | no           | any                                                                                                                                                                                                                     | Populated for `*_status_changed`-type events — the closest thing to a field-level diff                                   |
| `commitSha`                                                    | no, nullable | string                                                                                                                                                                                                                  |                                                                                                                          |

**Ownership:** append-only. Written by whatever performs the action —
today, a human or an AI agent finishing a task; eventually, a hook (§10).
**Never edited after creation** — this is the same discipline
`DECISIONS.md`/`FOUNDER_DECISIONS.md` already enforce for their own
entries ("do not renumber, reorder, delete, or rewrite the substance of
an existing entry"), applied to a log instead of a decision register.

**Validation rules:** entries are immutable — a validation pass that
finds an existing `id`'s content changed is a hard failure, not a warning;
`relatedTicketId` etc. must resolve if present; timestamps strictly
non-decreasing by `id` order.

**Note:** this is the Activity Feed's data source and the _foundation_ of
an audit trail, not necessarily a complete compliance-grade one — it
captures that a change happened and a one-line summary of it, not a full
before/after object diff for every field of every entity. If Formetrix
later needs the latter (e.g., for a real multi-user permission system),
that is a deliberate extension of this file, not something this design
silently assumes.

### `releases.json`

**Purpose:** structured form of `management/CHANGELOG.md`.

| Field                         | Required                 | Type                                         | Notes                                                                                                                                                                                                                                                                 |
| ----------------------------- | ------------------------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`                     | yes                      | string (semver)                              | e.g. `"0.1.0"`                                                                                                                                                                                                                                                        |
| `status`                      | yes                      | enum: `unreleased`\|`released`\|`yanked`     | `CHANGELOG.md`'s current `0.1.0` entry is explicitly "(Unreleased)"                                                                                                                                                                                                   |
| `workStartedDate`             | no, nullable             | date                                         | Supports date-range entries like the current one (`2026-07-29 to 2026-07-30`) without a loose freeform string                                                                                                                                                         |
| `releaseDate`                 | no, nullable             | date                                         | Null until actually released                                                                                                                                                                                                                                          |
| `note`                        | no, nullable             | string                                       | The "state of git history" callout `CHANGELOG.md` already uses, e.g. "not yet pushed to GitHub"                                                                                                                                                                       |
| `added` / `changed` / `fixed` | yes (may be empty array) | array of `{summary, ticketId?, decisionId?}` | Kept as first-class prose (`summary`), **not** forced into a ticket reference — some entries (e.g. "Repository created on GitHub") don't map to any ticket, and fabricating one would violate FORMETRIX.md's prohibition on inventing traceability that doesn't exist |

**Ownership:** curated, authored content — deciding what's release-note-
worthy is an editorial judgment call, not something to auto-generate from
`activity.json` wholesale (though `activity.json` is a reasonable
starting point for a human or agent drafting a release).

**Validation rules:** at most one `status: unreleased` entry at a time;
`releaseDate` required when `status: released`; every `ticketId`/
`decisionId` reference must resolve.

## 4.7 Cross-file relationships and the single-writer rule

```mermaid
flowchart LR
    Tickets["tickets.json"] -->|milestoneId — authoritative| Milestones["milestones.json"]
    Milestones -.->|ticketIds — derived, computed from the left| Tickets
    Tickets -->|dependencies[].ticketId| Tickets
    Decisions["decisions.json"] -->|relatedTicketIds| Tickets
    Decisions -->|supersedes / supersededBy| Decisions
    Releases["releases.json"] -->|ticketId / decisionId in entries| Tickets
    Releases -->|ticketId / decisionId in entries| Decisions
    Activity["activity.json"] -.->|relatedTicketId / relatedDecisionId / relatedMilestoneId, read-only pointers| Tickets
    Activity -.-> Milestones
    Activity -.-> Decisions
    ProjectStatus["project-status.json"] -.->|fully computed from all of the above| Tickets
    ProjectStatus -.-> Milestones
    ProjectStatus -.-> Activity
```

**The one rule that makes this whole graph safe:** every relationship
above has exactly one direction that's _authoritative_ (solid arrow) and,
where a reverse pointer exists for convenience (dashed arrow,
`milestone.ticketIds`), it is always _derived_ — recomputed by the
validation script, never hand-edited, never a second place the same fact
could be asserted differently. This is ADR-0017 (§13).

## 5. Progress Calculation Rules

### 5.1 Ticket `progressPercent`

```
if status == completed:        100
if status in {backlog, planned}: 0
if status in {in_progress, blocked}:
    if acceptanceCriteria is empty:
        50  (and raise a data-integrity warning — an in-progress
             ticket with no acceptance criteria is itself a defect)
    else:
        round(100 * count(acceptanceCriteria where met=true) / count(acceptanceCriteria))
```

### 5.2 Milestone `progressPercent`

```
progressPercent(milestone) = round(mean(progressPercent(t) for t in tickets where t.milestoneId == milestone.id))
0 if the milestone has no tickets yet.
```

**Worked example against this project's real data, as of FM-0024's own
completion (10 tickets under Milestone 0 at that point):**
FM-0001 (100, completed) + FM-0002 (67, 2 of 3 acceptance criteria met) +
FM-0003 (33, 1 of 3 met — "committed" is met, "pushed" and "verifiable on
pushed state" are not) + FM-0004 (0, planned) + FM-0005 (0, planned) +
FM-0006 (0, planned) + FM-0021 (100) + FM-0022 (100) + FM-0023 (100) +
FM-0024 (100, once this ticket completes) = 600 ⁄ 10 = **60%**.

This is meaningfully lower than the 80% currently hand-set in
`MILESTONES.md`. That gap is the single most important finding in this
document — see §14.

### 5.3 Project `overallProgressPercent`

```
overallProgressPercent = round(mean(progressPercent(m) for m in all milestones))
```

Equal-weighted per milestone, not per ticket — chosen so a milestone with
many small tickets doesn't dominate one with few large ones. This
weighting choice is a judgment call, not a fact; flagged in §15 as worth
the founder's explicit confirmation, with ticket-count-weighting as the
documented alternative.

## 6. Dashboard Information Architecture

Nine views, each with its primary data source and purpose. No UI is
designed here — this is what data each screen needs, not its layout.

### 6.1 Executive Overview

**Source:** `project-status.json`. The landing page: overall progress,
current milestone, ticket-status counts, repository push state, a
blocked-tickets teaser, a recent-activity teaser, and the data-integrity
warning count as a single visible number — a bug or drift shouldn't be
discoverable only by digging into another tab.

### 6.2 Milestone Timeline

**Source:** `milestones.json` (+ ticket rollups). Since no milestone
currently has a `startDate`/`targetDate` (§15), this view must degrade
gracefully: **sequence mode** (ordered list by milestone number, today's
only usable mode) vs. **calendar mode** (a real timeline, once dates
exist). It must never fabricate a date to make a Gantt chart render.

### 6.3 Ticket Kanban Board

**Source:** `tickets.json`. Columns = the five `status` values. Cards show
id, title, priority, type, owner. Filterable by milestone.

### 6.4 Roadmap View

**Source:** `milestones.json`, cross-checked against `docs/ROADMAP.md`'s
Phase 1/Phase 2/Future structure. This view is where Inconsistency I-2
(flagged in FM-0022/FM-0023 and still open) becomes directly visible: the
dashboard needs one roadmap vocabulary, and today there are two
(Milestones 0–5, and Phases 1/2/Future) that were never formally mapped to
each other. Recommendation: treat Milestones as authoritative for this
view (they have ticket-level granularity Phases don't), and flag
`docs/ROADMAP.md`'s Phase framing as a candidate for retirement — a
founder decision (§15), not something this document decides unilaterally.

### 6.5 Decision Log

**Source:** `decisions.json`. Filterable by `kind` (Architecture/Founder),
searchable, shows supersession chains and `relatedTicketIds` links.

### 6.6 Activity Feed

**Source:** `activity.json`. Reverse-chronological, filterable by `type`,
`actor`, or related entity.

### 6.7 Release History

**Source:** `releases.json`. Added/Changed/Fixed grouped per version,
linking back to tickets and decisions where a reference exists.

### 6.8 Risks and Blockers

**Source:** `tickets.json` (`status: blocked`, plus a **proposed
addition**: tickets `in_progress` with `lastUpdatedAt` older than a
configurable threshold — a genuinely useful staleness signal not in the
ticket's original request, flagged here as a recommendation, not an
existing requirement) and `milestones.json` (`status: blocked` or
non-empty `blockers`).

### 6.9 Data Integrity Warnings

**Source:** the output of the validation script (§10), not a JSON file of
its own. This view is the visualization of §8 — every rule listed there
that fails becomes a row here. It exists because this project has
_already_ needed exactly this three times over (FM-0021's missing file,
FM-0022's milestone-name mismatch, FM-0023's meeting-log sequencing
contradiction) — all caught by careful reading, none by a rule that runs
on its own.

## 7. Update Workflow

Once the tooling in §16 exists, a change flows in one direction:

1. A human, an AI agent, or a hook determines a fact has changed (a
   ticket's status, a new decision, a commit landing).
2. It is written to the relevant `management/data/*.json` file — the
   _only_ place it is written.
3. The validation script (§10) runs: schema check → referential integrity
   → recompute all derived fields (`progressPercent`, `ticketIds`,
   `project-status.json` in full) → regenerate the corresponding
   `management/*.md` section.
4. An `activity.json` entry is appended recording what changed.
5. The dashboard reads the refreshed JSON directly; Excel/PDF/GitHub
   Issues sync (§11–§12) read it on their own schedule, never writing back.

Until that tooling exists (§16), this workflow is entirely manual and
Markdown-first, exactly as it is today.

## 8. Validation Rules (consolidated)

Beyond what's listed per-file in §4:

- **Referential integrity:** every foreign-key-shaped field
  (`milestoneId`, `dependencies[].ticketId`, `relatedTicketIds`,
  `supersedes`, release entry references) must resolve to an existing
  record. An unresolved reference is a hard failure, not a warning.
- **Enum membership:** every `status`/`priority`/`type`/`kind` value must
  be one of its defined set.
- **No orphaned derived data:** `milestone.ticketIds` must exactly match
  the set of tickets whose `milestoneId` points at it — any mismatch means
  the derivation didn't run, not that the data disagrees with itself.
- **Immutability of `activity.json`:** covered in §4's activity.json
  section — repeated here because it's the one rule that, if violated,
  breaks the entire audit trail's premise.
- **Founder-decision authority:** no automated process may set a
  `kind: founder` decision's `status` to `approved`, or set a milestone's
  `status` to `complete` (per the ticket's own "do not mark a milestone
  complete without Founder approval").
- **Status-transition looseness, deliberately:** this design does **not**
  enforce a strict status state machine (e.g., forbidding `backlog` →
  `completed` directly). This project's real history already includes
  tickets that skipped `in_progress` entirely (FM-0021, FM-0022, FM-0023
  all went straight to `completed`). Over-constraining this would fight
  how the team actually works.

## 9. Audit Trail

`activity.json` (§4) is the audit trail's foundation: an immutable,
timestamped, actor-attributed record of every change. Combined with each
entity's `lastUpdatedAt` and (for tickets) `commitSha`, this answers "what
changed, when, by whom, and which commit made it true" for anything in
the system — directly serving FORMETRIX.md §7's traceability requirement,
extended from product data to the project-management data itself.

## 10. Automation Design (not activated in this ticket)

**Deterministic local validation script** — `scripts/validate-project-data.mjs`
(or `.ts`), run via a new `npm run validate:data`, consistent with this
repo's existing `npm run lint`/`typecheck`/`format:check` convention. It
performs the entire §7 pipeline (steps 2–4) and exits non-zero on any §8
hard failure — the same shape FM-0004's planned CI workflow already
expects to run scripts against.

**Claude Code hook touchpoints** (conceptual — exact hook event names and
config should be verified against current Claude Code documentation at
implementation time, not assumed from this document):

- **After ticket status change:** append an `activity.json` entry with
  `previousValue`/`newValue`, then run the validation script to recompute
  affected rollups.
- **After task/ticket completion:** verify `acceptanceCriteria` against
  mechanically-checkable repo state where possible (files exist, lint
  passes) before allowing `status: completed` — flip status only when
  every criterion is verifiably met or a human/agent explicitly overrides
  with a note, never silently.
- **On session stop:** a read-only validation pass (§8), not a status-
  mutating one — surface newly-found warnings without changing any data.
- **On commit creation:** this is naturally a **git hook** (or a CI step),
  not strictly a Claude Code hook, though Claude Code can also observe
  commits it makes within its own session. Either way, it parses the
  commit message for an `FM-XXXX:` prefix — **already this project's real
  convention**, visible in `git log` today (`7e0db87 FM-0001: Initialize
Formetrix foundation`) — and sets that ticket's `commitSha`.

No hook is installed by this ticket. This section is a design brief for
FM-0004 (CI) and a future automation ticket to implement against.

## 11. Excel Export (future, generated only)

A generated workbook, produced from the JSON files, never hand-edited —
if it needs to be, that's a sign a dashboard view is missing, not a
reason to make Excel a write surface. One sheet per JSON file is the
simplest mapping (Tickets, Milestones, Decisions, Releases), plus a
Summary sheet mirroring `project-status.json`.

## 12. PDF Snapshots (future, generated only)

Same rule: generated from JSON at a point in time, immutable once
produced — directly consistent with `docs/DOMAIN_MODEL.md`'s existing
Report entity design (FD-0009: immutable, versioned snapshots). A future
PDF "project snapshot" export is conceptually the same kind of artifact
as a Report, just scoped to project-management data instead of property
data — worth building on the same underlying pattern when both exist.

## 13. GitHub Issues Synchronization (future)

The highest-risk future integration in this design, because GitHub Issues
is a system this project doesn't control the write surface of — a founder
or collaborator can edit an Issue directly in GitHub's UI at any time.
Bidirectional sync between two independently-editable systems is a
well-known hard consistency problem. **Recommendation: one-way sync only**
at least initially — either JSON → GitHub Issues (Issues become a
read-only mirror for external visibility) or GitHub Issues → JSON (if
external contributors need to file tickets), but not both directions at
once. Which direction is a founder decision (§15), not an engineering
default — it depends on who's expected to use GitHub Issues and why.

## 14. Risks

1. **Progress-formula sticker shock.** §5.2's computed Milestone 0
   progress (~60%, and lower still once FM-0025 and further tickets are
   added under it) is notably lower than the 80% currently hand-set in
   `MILESTONES.md`. This
   will look like a regression if the founder isn't aware going in — it
   isn't one; it's a more honest number replacing a generous one. Flagged
   here explicitly rather than left to be discovered.
2. **Migration cost and transcription risk.** Backfilling 24 tickets, 16
   ADRs, and 9 FDs into JSON accurately is real, non-trivial work.
   Mitigation: the migration script should diff its regenerated Markdown
   against what's actually committed and flag any content difference for
   human review, never silently overwrite.
3. **Dual-source drift, if single-writer discipline isn't actually
   enforced.** This is the core risk the whole design exists to prevent
   (§4.3) — it's only closed if the pre-commit/CI check described there
   actually gets built, not just designed.
4. **Solo-founder JSON ergonomics.** Hand-editing JSON is worse than
   editing Markdown for a single founder working alone. Mitigated by: (a)
   this is why the dashboard itself, not raw JSON editing, should become
   the primary write interface once built, and (b) nothing about this
   design requires adopting it before that interface exists.
5. **Scale-appropriateness.** FORMETRIX.md §21 and §8's Decision Filter
   both ask "are we adding complexity before it's needed?" At 24 tickets
   and a solo-founder-plus-AI-agent team, six JSON schemas, nine dashboard
   views, and a validation pipeline is a substantial system for the
   project's current size. This document was scoped as architecture-only
   specifically so that question can be answered by the founder _before_
   committing engineering time to it (§15) — this design doc's existence
   doesn't imply it should be built now.
6. **Vocabulary inconsistencies surfaced, not yet fixed.** `Accepted` vs.
   `Approved` (§4's decisions.json), and Inconsistency I-2 (Phase vs.
   Milestone framing, §6.4) — both real, both pre-existing, neither
   created by this document, neither silently resolved by it either.
7. **GitHub Issues sync is the least-controlled integration** — see §13.

## 15. Founder Decisions Required

None of the following were decided by this document — each needs
explicit founder input before implementation:

1. **Approve or revise the progress-computation formula** (§5) — it will
   show lower numbers than today's hand-set percentages. Is the
   equal-weighted-per-milestone project rollup (§5.3) right, or should it
   be ticket-count-weighted instead?
2. **Should milestones adopt real `startDate`/`targetDate` values**, or
   stay date-less with only qualitative sequencing, as today?
3. **Is JSON-primary-with-generated-Markdown (§4.2) the right end state**,
   or is Markdown-primary-with-derived-JSON (option B, §4.1) preferable
   given the solo-founder ergonomics risk (§14.4)?
4. **Should `docs/ROADMAP.md`'s Phase framing be retired** in favor of
   Milestones as the one roadmap vocabulary (§6.4)?
5. **Is this worth building now**, given §14.5's scale-appropriateness
   question — or should it wait for more project history to justify it?
6. **GitHub Issues sync direction** (§13), if pursued at all.

## 16. Recommended Implementation Sequence

Not "build everything in §4–§13" — a deliberately small first step that
tests the schema against real data before committing further:

**FM-0025 (recommended next ticket): build `scripts/validate-project-data.mjs`
and backfill `management/data/*.json` for Milestone 0 only** (its 10
tickets, plus the ADRs/FDs that reference them) — not all 24 tickets and
25 decisions at once. This validates the schemas in §4 against real,
messy, already-written content (including FM-0004's dependency note and
FM-0021's ID-collision annotation) before deciding whether to migrate
everything else. If Milestone 0's migration reveals the schema is wrong
in some way, that's cheap to fix at 10 tickets and expensive to fix after
migrating all 24.
